proof it has run. Update it when the network-enabled full build is verified.

- The Gradle 9.7.0 binary distribution and wrapper JAR match published SHA-256 checksums.
- Domain/application code and its tests compile directly with Java 25, `-Xlint:all,-processing`, and `-Werror`.
- All 55 selected JUnit tests pass: 33 core tests plus 22 DynamoDB adapter and local-initializer cases.
  These use cached JUnit 6.0.3, AssertJ 3.27.7, Quarkus 3.33.3.1 annotations, and AWS SDK 2.21.40.
  This is a limited offline compatibility check, not validation of the pinned Gradle dependency graph.
- Selected HTTP/filter and DynamoDB/wiring sources compile with Java 25 and source warnings as errors;
  optional third-party classfile-annotation warnings are excluded, as in the build.
- Java sources are formatted with cached Google Java Format 1.19.1 on JDK 21. The pinned formatter
  remains to be run through Spotless during network-enabled verification.
- Shell scripts pass shell syntax checks.
- Seven maintenance-script tests pass, including release version/tag/API guards and archive layout checks.
- TOML references, YAML/XML/JSON syntax, full action SHA pins, and local documentation links validate.

## Pending environmental verification

A subsequent local Gradle daemon log exposed a Kotlin DSL compilation error in the release copy
specification and deprecated task-registration declarations. These have been corrected. Dependency
refresh now resolves its baseline before running checks and explicitly disables configuration caching
for all maintenance passes, including when user-level Gradle settings enable it. Shell syntax checks
and all seven maintenance tests pass after this fix; a complete Gradle rerun remains blocked here.

The subsequent SpotBugs main report identified a null-pointer catch in DynamoDB decoding and an
intentional shared BlobStore constructor reference. Decoding now validates stored attributes explicitly;
the dependency-injection exclusion is limited to that constructor field and bug pattern. Full main
sources compile on Java 25 against the resolved runtime classpath. Running SpotBugs 4.10.5 directly
with the configured filter, maximum effort, and medium confidence produces zero findings, zero errors,
and zero missing classes. All 64 unit and architecture tests pass against the cached resolved test
classpath, including new malformed-metadata cases. The Gradle task itself and integrations were not
rerun in this sandbox for this fix.

IDE source verification has also been populated: all 181 unique source archives in the latest IDE
failure report match exact SHA-256 entries computed from their cached files. No existing checksum
was replaced and no trust exemption was added. All 11 maintenance tests pass, including recorder
idempotency, refusing mismatches/conflicting cache copies, and excluding unpinned components.
Dependency refresh now requests published sources and records cached IDE archives; the new Gradle
source-resolution task has been API-checked but cannot be executed under this sandbox's socket restriction.

The IDE also requested Kotlin reflection bundled with Gradle, which was outside the project dependency
graph. Its exact 2.4.0 source and POM checksums are now recorded. Source maintenance explicitly resolves
Gradle's embedded Kotlin libraries, and the cache recorder covers POM/module metadata for pinned
components as well. All 12 maintenance tests pass, including refusing metadata checksum replacements.

Maintenance hashing now uses a streaming SHA-256 implementation compatible with Python 3.9; the
previous `hashlib.file_digest` call required Python 3.11 and failed under the interpreter selected by
the user's Gradle environment. Empty-file and multi-chunk hashing are covered by a regression test.

Dev-launcher lock maintenance now invokes Quarkus's command-export mode, confirmed against the pinned
3.40.1.1 plugin sources, to exercise its lazily created bootstrap resolver without starting a server.
All 16 maintenance tests pass on Python 3.9.6, including mocked checks that the export flag is always
present, strict verification follows lock generation, and failures stop the script. Actual dev-mode
lock generation still requires running the repair command outside this socket-restricted sandbox.
